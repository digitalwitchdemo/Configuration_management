# Kubernetes manifests for the OpenTelemetry Demo

Hand-derived from `compose.yaml` + `compose.full.yaml` + `compose.observability.yaml`
+ `compose.agent.yaml` (i.e. the full `docker compose -f compose.yaml -f compose.full.yaml
-f compose.observability.yaml -f compose.agent.yaml up` stack: 24 custom-built services
plus Postgres, Valkey, Kafka, Jaeger, Prometheus, Grafana, and OpenSearch).

## Layout and apply order

Directories are numbered in dependency order. Run `./deploy.sh`, or apply them by hand
in the same order - each stage's workloads must be Ready before the next stage (which
depends on them) is applied:

| Stage | Contents |
|---|---|
| `00-namespace` | the `otel-demo` namespace |
| `01-storage` | `StorageClass` (AWS EBS `gp3`, dynamic provisioning) + an optional static `PersistentVolume` example |
| `02-config` | every `ConfigMap` and `Secret` (see below) |
| `03-pvc` | `PersistentVolumeClaim`s for Postgres, Valkey, Kafka, OpenSearch, Prometheus, Grafana |
| `04-datastores` | `StatefulSet`s: `astronomy-db` (Postgres), `valkey-cart`, `kafka` |
| `05-telemetry-backends` | Jaeger, Prometheus, OpenSearch, OpAMP server |
| `06-otel-collector` | the OTel Collector (waits on the backends above) |
| `07-flagd` | flagd + flagd-ui (waits on the collector) |
| `08-platform-services` | services with no app-tier peer dependency: currency, email, payment, quote, shipping, ad, image-provider, telemetry-docs, product-catalog, grafana |
| `09-mid-tier` | cart (→ valkey), recommendation (→ product-catalog), accounting/fraud-detection (→ kafka) |
| `10-checkout` | checkout (→ cart, currency, email, payment, product-catalog, shipping, kafka) |
| `11-frontend-tier` | frontend, then mcp → agent → chatbot, then load-generator |
| `12-edge` | frontend-proxy (Envoy) - the ingress, applied last because it depends on almost everything |

**Runtime enforcement, not just apply-order**: every app Deployment also carries a
`wait-for-deps` `initContainer` that TCP-polls its actual dependencies' Service DNS
names before the main container starts (mirroring compose's `depends_on: condition:
service_healthy`). So even a `kubectl apply -f k8s/` across every directory at once
(instead of running `deploy.sh`) will still come up in the right order - pods just sit
in `Init:0/1` until what they need is reachable.

## Before you apply

1. **Images**: every custom-built service (the 24 in `.github/workflows/ecr-build-push.yml`)
   is set to `<AWS_ACCOUNT_ID>.dkr.ecr.<AWS_REGION>.amazonaws.com/ecomerce/<service>:latest`.
   Replace `<AWS_ACCOUNT_ID>`/`<AWS_REGION>` everywhere, e.g.:
   ```bash
   grep -rl 'AWS_ACCOUNT_ID' k8s | xargs sed -i 's/<AWS_ACCOUNT_ID>/123456789012/g; s/<AWS_REGION>/us-east-1/g'
   ```
   The 7 vendor/upstream images (Postgres, Valkey, flagd, Jaeger, Prometheus, Grafana,
   the OTel Collector Contrib distro) are left pointing at their public upstream registries.
2. **EBS CSI driver**: `01-storage/storageclass.yaml` uses `ebs.csi.aws.com`. Install the
   [Amazon EBS CSI driver add-on](https://docs.aws.amazon.com/eks/latest/userguide/ebs-csi.html)
   on the cluster first, or PVCs will stay `Pending` forever.
3. **Secrets**: `02-config/secret-postgres.yaml` ships the same plaintext demo passwords
   already in this repo's `.env` and `src/postgresql/init.sql` - change both together if you
   deploy this anywhere real. `02-config/secret-llm.yaml` ships an empty `API_KEY`; the
   agent replays the fixtures in `agent-fixtures` (from `src/agent/fixtures/vcr_cassettes`)
   instead of calling a live LLM until you fill one in.
4. **Grafana provisioning**: `grafana.ini` and the datasources/dashboard-provider configs
   are static `ConfigMap`s in `02-config/`. The alerting rules (~900 lines) and the actual
   dashboard JSON (~17.7k lines across 10 files) are generated by `deploy.sh` at apply time
   via `kubectl create configmap --from-file=...` instead of being hand-inlined here.

## Known simplifications vs. compose

- **`otel-collector`**: `otelcol-config.yml`'s `docker_stats`/`host_metrics` receivers
  assume a Docker host (`/var/run/docker.sock`, `/hostfs`) that doesn't exist on a k8s
  node. Those two receivers are left in the mounted config as-is (so it matches compose
  byte-for-byte) but will just fail to scrape - swap them for `kubeletstats`/`k8sobjects`
  receivers for a real cluster.
- **`opensearch`**: `bootstrap.memory_lock` is set to `false` here (compose sets it `true`
  with unlimited ulimits) so the pod runs without needing the `IPC_LOCK` capability or
  host-level ulimits on arbitrary nodes.
- **`flagd-ui`**: mounts the same flag definitions flagd reads, but as a read-only
  `ConfigMap` volume - edits made in the flagd UI won't persist across pod restarts the
  way they do with compose's read-write bind mount. Swap for a PVC seeded from the
  ConfigMap (an init container copying it in on first start) if that matters to you.
- **`accounting`**: compose's `depends_on` for this service lists only `kafka` and
  `otel-collector`, even though it needs Postgres too. The `wait-for-deps` init container
  here additionally waits on `astronomy-db`, since otherwise the pod would crash-loop
  until Postgres happened to be reachable.
- Every container runs as a `Deployment` with `replicas: 1` - no `HorizontalPodAutoscaler`
  or `PodDisruptionBudget` is included; add them if you need more than a functional demo.
- **`frontend-proxy`**'s `Service` is `LoadBalancer` type but only exposes Envoy's proxy
  port (8080), not its admin port (10000, which can change runtime config/drain
  listeners) - unlike compose, which publishes both to the host for local convenience.
  Reach the admin port with `kubectl -n otel-demo port-forward deploy/frontend-proxy
  10000:10000` instead.
